# M4d 实施记录：玩家身份与实体自定义名称

状态：已实施（2026-11-04）
范围：[roadmap.md](../roadmap.md) 第 7 节 M4 的第四个增量
结论：会话能回答“那具 `PLAYER` 实体是谁”——玩家列表把 UUID 映射到用户名，
实体快照带上服务端设置的自定义名称；两者到达顺序任意，查询时关联即可。

## 1. 起点：实体只知道“有个人”

M4b 落地后，实体表里能读到 `type=PLAYER` 的实体与它的 UUID，但看不到名字：
`ClientboundAddEntityPacket` 只有 UUID，用户名在**玩家列表**里，是另一个包。
对机器人场景来说这是硬缺口——“视野里有个人”和“是 Alice”是两件事。

另一个缺口是名牌：生物与掉落物的显示名走实体元数据（`ClientboundSetEntityDataPacket`），
M4b 明确把元数据留在了范围之外。

## 2. 玩家列表：按 UUID 合并，按包上报

`ClientboundPlayerInfoUpdatePacket` 的语义比名字暗示的窄：一个包只带 `actions` 声明的
那几列。服务端会把同一个人拆成多次更新——先 `ADD_PLAYER` 给档案，再 `UPDATE_LATENCY`
给延迟，换模式时再来一次 `UPDATE_GAME_MODE`。因此适配层必须自己合并：

| 列 | 合并规则 |
| --- | --- |
| 用户名 | 本包带 `ADD_PLAYER` 才更新，否则沿用上一状态 |
| 游戏模式 | 本包带 `UPDATE_GAME_MODE` 才更新，否则沿用上一状态（没有上一状态时用包里的默认值） |
| 延迟 | 本包带 `UPDATE_LATENCY` 才更新，否则沿用上一状态 |

“沿用上一状态”不是宽容，而是必需：先到延迟、后到档案的顺序很常见，若把缺失字段当成
“清空”，刚拿到的用户名会被下一次延迟更新抹成 `null`。

合并后**没有任何变化就不上报**。`UPDATE_LISTED`、`UPDATE_LIST_ORDER`、`UPDATE_HAT`
这类字段本层不关心，它们不该变成事件。

事件粒度是**一个包一个事件**（`PlayerListChanged(updated, removed)`），不是一条目一个。
原因与 M4a 把区块移出有界队列相同：条目数由服务端人数决定，按条投递会让大服的一次登录
把缓冲打满，而缓冲写满在本项目里的语义是终止会话。

`ClientboundPlayerInfoRemovePacket` 对称处理，只是把条目从表里摘掉。

## 3. 实体元数据：只读下标 2

元数据是一张“下标 → 值”的表。下标由协议版本固定，但**含义取决于实体层级**：

- 下标 0–7 是所有实体共有的字段，其中下标 2 是自定义名称（可选文本组件）；
- 生物层级的字段从这个基址往后排，例如生命值是 9。

协议包不携带层级信息，本层也没有实体类型表。因此只读下标 2——它对所有实体都成立。
反过来，如果按“生物都下标 9”去读血量，落在非生物实体上就是另一个字段的值，
那不是数据缺失，而是错误数据。

字段存在但为空表示服务端要求**清掉**名牌；字段不出现才表示“本包没提这件事”。
两者必须区分，否则随机到达的状态包会把名牌抹掉。

## 4. 分层

| 层 | 职责 |
| --- | --- |
| `McplConnection` | 合并玩家列表分片、读取元数据下标 2、维护网络线程私有的 `LinkedHashMap<UUID, RemotePlayer>` |
| `Session` | 缓存玩家列表（写缓存 → 发事件）、提供 `players` / `player(uuid)` / `playerCount` / `nameOf(entityId)` |
| 调用方 | 只看到不可变快照，不需要知道包是分几次到的 |

`nameOf(entityId)` 是**查询时关联**（实体 UUID → 玩家列表），不是把名字复制进实体快照。
两者到达顺序不固定，复制一份就要处理“名字后到、快照过期”的同步问题；查询时关联没有这个状态。

玩家列表是**会话级**事实：换维度不清空（人不会因为进了下界就从 Tab 列表消失），
而区块与实体在换维度时清空。这一条在 M4c 的清理路径里显式标注。

## 5. 验证

`ClientSessionTest.玩家列表与自定义名称可从会话查到`（真实 Minestom，两个并发会话）：

- 观察者先登录，玩家列表里出现**自己**（Tab 列表是“服务器上都有谁”，不只是别人）；
- 第二个玩家登录后，观察者收到 `PlayerListChanged`，`player(uuid).name` 与服务端用户名一致；
- 关联链路打通：玩家实体出现在实体表里，`nameOf(entityId)` 返回用户名，实体 UUID 与
  玩家列表条目的 UUID 相同；
- 僵尸挂上自定义名称后，`entity(id).customName` 与服务端设置的文本一致；改名后再次一致；
- 非玩家实体 `nameOf` 返回 `null`：它不在玩家列表里，没有名字可关联；
- 关闭会话后 `playerCount == 0`。

CLI 现场证据（两个客户端先后登录同一 harness）：

```text
event=players updated=[PlayerTwo] removed=[]
event=players updated=[PlayerOne] removed=[]
event=entity.spawned id=1 type=PLAYER x=0.5 y=40.0 z=0.5
chunk x=0 z=0 minY=-64 sections=24 cached=17 entities=1 players=[PlayerOne, PlayerTwo] ...
event=players updated=[] removed=[fbc31858-...]     # PlayerOne 下线
```

`./gradlew build` 通过；模块边界与字节码断言未变化。

## 6. 与计划的偏差

| 计划（M4c 结束时的设想） | 实际做法 | 原因 |
| --- | --- | --- |
| 实体元数据“全量转发” | 只读下标 2 | 没有实体类型表时，其余下标无法判断层级归属 |
| 玩家列表按条目发事件 | 按包发一个事件 | 大服一次登录会把有界缓冲打满，而溢出等于终止会话 |
| 把用户名写进实体快照 | 查询时关联 | 两个包到达顺序不固定，复制会引入同步状态 |
| 顺带提供血量 | 不做 | 血量下标依赖“是否属于生物层级”，没有类型表就会读到错误字段 |

## 7. 已知限制与下一步

- 玩家列表的显示名（`UPDATE_DISPLAY_NAME` 的文本组件）、队伍颜色、皮肤属性未处理；
  这些属于 Tab 列表的呈现细节，不进入核心。
- 实体元数据只覆盖自定义名称。血量、姿势、装备、状态效果需要本地实体类型表或独立子系统。
- 玩家列表是会话级缓存，不提供“谁刚刚加入”的增量语义之外的排序保证；
  `players()` 返回副本，按 UUID 索引，不保证顺序。
