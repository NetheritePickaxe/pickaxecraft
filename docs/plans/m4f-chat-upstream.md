# M4f 实施记录：聊天上行

状态：已实施（2026-11-04）
范围：[roadmap.md](../roadmap.md) 第 7 节 M4 的第六个增量
结论：会话能发消息了。`Session.sendChat` / `sendCommand` 把文本交给服务端，服务端广播回来的
那条消息以 `ChatReceived` 回到事件流与聊天记录——本端不做本地回显。

## 1. 起点：能读不能写的会话

M4e 之后会话能读三类聊天，却发不出一个字。上行不是“把字符串塞进包”这么简单，它牵出
三件在接收方向上不存在的事：**签名**（谁证明这条消息是我发的）、**last-seen 窗口**
（我确认了哪些消息）、**阶段**（play 之前发聊天是协议错误，不是静默丢弃）。

## 2. 签名：离线可发，在线要密钥

26.2 的 `chat_message` 带 `signature`（256 字节，可空）、`timestamp`、`salt` 与 last-seen 三件套。

- 本层发**不带签名**的消息（`signature = null`）：离线模式的服务端接受这种消息，
  这也是当前唯一能支持的场景。
- 启用安全聊天的在线服务端要求每条消息由会话密钥签名，密钥来自微软认证链路——属于 M5。
  本层不做“半个签名”：伪造签名比不签更糟，它会以校验失败的形式断在服务端。

`timestamp` 取发送时刻（`System.currentTimeMillis()`），`salt` 恒为 0——盐只在签名里起作用，
不签名的消息没有可被重放的签名。

## 3. last-seen 窗口：空位集是真的

上行包里的 `ackOffset` / `ackList`（固定 20 位）/ `checksum` 描述“客户端确认看到了哪些消息”。

本端一律填 **偏移 0、位集全空、校验 0**。这不是占位符，而是准确的事实：本端从不为收到的
消息生成签名确认。填一个假的“已看到”反而会与服务端记录的待确认序列不一致——那是主动制造
不一致，而不是省略一个字段。

注意这条与 M4e 的 `ServerboundChatAckPacket` 不是一回事：后者是接收方向的确认
（“我收到了几条”），上面这三个字段是发送方向随消息携带的确认快照。两者独立，都要维持。

## 4. 命令走另一个包

`ServerboundChatCommandPacket` 只有一个字符串字段，不参与聊天签名，因此在启用安全聊天的
服务端上同样能用（能否执行仍取决于玩家权限）。包里的命令**不带**前导斜杠，调用方按习惯写
`/help` 时由适配层剥掉一层；`//help` 剥成 `/help`，不会被悄悄改写成 `help`。

## 5. 分层与 API

| 层 | 职责 |
| --- | --- |
| `ChatInput` | 校验并规范化输入：长度上限、单行、剥一层斜杠 |
| `McplConnection` | 阶段/连接状态前置检查；编码 `chat_message` 与 `chat_command` |
| `ProtocolConnection` | `sendChat` / `sendCommand`，校验在最外层先做 |
| `Session` | 状态检查（必须 play），把包交给连接；不本地插入、不猜结果 |
| 调用方 | 发完继续读事件流；回执就是服务端广播回来的那条消息 |

`Session.sendChat` 是非挂起函数：写入网络是异步的，返回不代表服务端已收到。没有“发送成功”
事件——真正的回执是那条广播回来的消息，额外造一个回执只会多一个可能与事实不符的信号。

## 6. 校验：长度、单行、斜杠

- **长度**：聊天与命令都是 256 个字符。这与服务端解码时的限制是同一个数字（Minestom 的
  `ClientChatMessagePacket` / `ClientCommandChatPacket` 都在构造时校验），超长会被断开。
- **单行**：协议允许字符串带换行，但下游一律按单行渲染；放过去等于让对端在任何朴素实现里
  伪造出一行自己没说过的话。这是本层额外加的限制。
- **空白**：空串与纯空白直接拒绝——服务端收下也只会广播一行空白。

校验在发出前失败，抛 `IllegalArgumentException`；会话状态不对时抛 `IllegalStateException`，
消息里带当前状态。两者都不会把会话打断，联调用例专门断言了“校验失败后仍在 play”。

## 7. 验证

`ChatInputTest`（8 例）：原样返回、空串与纯空白、256/257 边界（按字符计，汉字同样）、换行与
`\r`、前导斜杠剥离、只剥一层、空命令、命令的长度与换行。

`ClientSessionTest.发送的聊天与命令服务端可见`（真实 Minestom）双证据链：

- **服务端侧**：harness 监听 `PlayerChatEvent` 与 echo 命令执行器，用例断言服务端收到的
  原文是 `你好，服务端`、命令输入是 `pickaxe hello world`（带空格的参数原样到达）。
- **客户端侧**：广播回来的消息以 `ChatReceived` 到达并进入 `session.chat()`。
- **边界**：257 字符、`/` 空命令在本地失败；关闭后发送被拒绝，异常消息里带 `CLOSED`。

`testing:minestom` 的 harness 为此加了三件东西：`PlayerChatEvent` 事实登记、一个 echo 命令
（`pickaxe`，带 `StringArray` 语法以便带参数）、以及 `awaitPlayerChat` / `awaitCommand` 两个
等待入口。命令事实按「谁执行了什么」登记，不依赖聊天广播。

CLI 现场证据（`connect ... --say "你好，服务端"`）：

```text
chunk x=0 z=0 minY=-64 sections=24 cached=17 entities=0 chat=0 players=[SayBot] block=(0, 40, 0):0 below=1
event=chat.sent text=你好，服务端
event=chat kind=system fmt=null text=SayBot: 你好，服务端
```

服务端侧同时打印 `event=player.chat name=SayBot message=你好，服务端`。

## 8. 一个测量到的差异：Minestom 用可翻译组件广播

第一次跑联调时回显是 `text=chat.type.text`：Minestom 广播玩家聊天时用的是可翻译组件
（`chat.type.text` + 参数），而本客户端没有语言文件，只渲染出键名，参数被丢掉。真实服务端
走的是带签名的 `player_chat` 包（M4e 已验证），与这条路径不同。

因此 harness 把 `PlayerChatEvent` 的格式改成字面文本 `名字: 正文`，让回显可以与原文对账；
用例同时断言 `kind=SYSTEM`——这是 Minestom 的选择，不是本层的推断。

## 9. 与计划的偏差

| M4e 结束时的设想 | 实际做法 | 原因 |
| --- | --- | --- |
| 上行需要签名，属于在线模式才做 | 做无签名上行 + 命令 | 离线模式是当前唯一可验证场景，无签名消息合法；签名留给 M5 |
| 本地插入一条“自己发的”消息 | 不插入 | 服务端可能过滤、改写或拒收；本地插入会让界面与服务端不一致 |
| 发送成功给一个回执事件 | 不给 | 服务端广播回来的消息就是回执，再造一个是冗余信号 |
| last-seen 字段可以填 0 了事 | 空位集 + 注释说明语义 | 0 恰好是正确值，但必须写清“为什么是 0”，否则下一个人会当成占位符 |

## 10. 已知限制与下一步

- 在线模式（微软认证 + 会话密钥 + 每条消息签名）未做，属于 M5；本层对安全聊天服务端会表现为
  消息被拒，而不是静默丢弃。
- 没有本地回显，因此发送到收到广播之间有网络往返的延迟；需要即时反馈的下游自己按“正在发送”
  状态处理。
- 命令没有补全：`ServerboundCommandSuggestionPacket` 与服务端下发的命令树还没处理，
  调用方得自己知道命令名。
- 客户端设置里的聊天可见性固定为 `FULL`；`/ignore` 之类的服务端过滤仍然生效，本层不参与。
