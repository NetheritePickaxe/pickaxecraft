状态：已评估（2026-11-03，基于对现有架构文档与外部生态证据的复查）
日期：2026-11-03
涉及：`docs/architecture.md` §2 技术栈、§3 协议策略、§5 会话与并发、§6 libGDX 与平台约束；`docs/roadmap.md` M1/M2/M3；[决策 0001](0001-protocol-backend.md) 的 Android 风险表述

## 1. 评估范围与总体结论

本文档汇总 2026-11-03 对 PickaxeCraft 现有技术栈与实现路径的完整复查结论，包括：协议层选型、网络层、并发模型、版本锁定策略、里程碑时序、Android 替代方案等全部评估项，并固化为可执行决策。

**总体结论：**

1. 技术栈选择是合适的，MCProtocolLib 是当前 JVM 生态能做出的最合理决策，经 PojavLauncher、rfresh2 fork 等证据复查后维持不变。
2. 实现路径大体合理，但存在一处内在矛盾——roadmap 自认「当前最大风险是 Android 上的 Netty」，却把 Android 验证（M3）排在 M2 之后，该时序需要调整。
3. 对原架构文档中「Netty on Android 不会直接崩」的表述需要修正：风险不在 Netty 本身，而在 PickaxeCraft 当前选定的运行时路径（ART + D8 反糖）；自带 OpenJDK 路径已被 PojavLauncher 生态验证可行。

## 2. 技术栈分项评估

| 维度 | 评估 | 关键依据 | 建议 |
| --- | --- | --- | --- |
| 协议层：MCProtocolLib 26.2 | ✅ 合适 | Geyser 生产验证、MIT、自带注册表 NBT、探针 120 行代码 0 行协议实现跑通 | 维持；补 API 稳定性评估与 EventLoopGroup 归属显式化 |
| 会话/并发：协程 + Actor | ✅ 合理 | 单 Actor 顺序处理 + 有界队列是流式协议处理的标准做法 | 补充跨线程桥接的显式设计（见 §5） |
| 网络：Netty 4.2.x | ✅ 桌面合适 / ⚠️ Android 视路径而定 | Netty 官方不支持 Android；4.2.4+ 在 ART 路径上有实测 VerifyError；OpenJDK 路径已被 Minecraft 原版验证 | M3 升级为双路径验证（见决策 3） |
| 字节码策略：Java 21 产物 | ✅ 方向正确且价值提升 | 同时服务 ART 反糖路径与 OpenJDK 直接加载路径 | 必须维持 |
| 版本锁定策略：26.2 跟随 Minestom | ⚠️ 有隐性成本 | Minecraft 2026 起季度 Drop（26.1 三月、26.2 六月、26.4 十月快照已测试）；上游 latest 已为 26.3-2 | 升级流程脚本化 + 每周上游探针（见决策 5） |
| 模块划分与构建门控 | ✅ 优秀 | `verifyBytecode` + `verifyModuleBoundaries` 是现有文档中最扎实的部分 | 维持 |

### 2.1 协议层的使用税（文档中需补强的两点）

MCProtocolLib 的选型经得起推敲，但有两个隐性成本在决策 0001 中提得不够重：

1. **上游 API 不承诺稳定**。rfresh2/MCProtocolLib（活跃 fork，服务 ZenithProxy）的自述明确写着「不为他人维护，对 API 稳定性不做任何保证」——说明深度使用方最终都走向 fork。项目应在 M1 期间评估：若需要 `Session.getChannel()` 之外的底层干预（自定义压缩管道、底层错误恢复等），是提 PR 给上游还是接受 fork。该决定越早做成本越低。
2. **生命周期归属已有前车之鉴**。MCPL 历史上存在 `nioEventLoopGroup` 线程阻止 JVM 退出的老 issue，社区结论是应由调用方提供 EventLoopGroup。architecture.md §5 已写「EventLoopGroup 必须随会话关闭」，方向正确，但建议在 M1 就把「EventLoopGroup 归调用方注入还是 Session 内部持有」写成显式 API 决策，而非默认实现。

**生态替代品核查结论（决策 0001 结论维持）：**

- **kmcprotocol**（Kotlin + PrismarineJS minecraft-data 生成多版本包类）、**kt-mc-packet**（Kotlin Multiplatform + kotlinx.serialization）：理念上更贴近原自研方案，但均无 Geyser 级生产验证。
- **hl-mc-kt**（现成 Kotlin Headless 客户端）：最终也是站在 MCProtocolLib 之上构建，从侧面验证「MCPL + 自研上层」是该赛道的事实路线。
- **ViaVersion**：只解决服务端多版本翻译，不提供客户端库能力，不构成替代。

## 3. Netty on Android 风险：表述修正与证据

### 3.1 原「不会直接崩」的表述过于乐观

外部证据显示：

- **Netty 官方不支持、不在 Android 上做测试与发布验证**。
- **Netty 4.2.4 及以上在 Android 8–12 存在实测 `java.lang.VerifyError`**：`UnpooledDirectByteBuf` 的字段类型校验失败导致类加载被拒，仅在 Android 13+ 正常。此问题在 Netty 4.2.x 后续版本已修复，但 PickaxeCraft 锁定的 4.2.1.Final 处于修复前的窗口期，需在 spike 中实测确认。
- **版本钉死与 CVE 的张力**：Netty 4.2.16.Final 一次性包含 11 个 CVE 修复（memory exhaustion / zip bomb / CR/LF injection 等）；4.2 迁移指南还更改了默认端点校验（hostname verification）行为。锁定 4.2.1.Final 意味着这些修复需要通过升级动作单独评估，而不能依赖传递依赖自动跟进。
- **前例**：gRPC-Java 面对同样问题时，官方结论是「Android 上别用 Netty」，转而提供基于 OkHttp 的轻量传输（`grpc-okhttp`，官方 javadoc 自述 "mainly for use on Android (client-only)"）。这证明「fork 协议库 + 自写传输」是有业界先例的降级路径，而非理论选项。

### 3.2 反向证据：PojavLauncher 证明 OpenJDK 路径完全可行

- PojavLauncher 在 Android 上运行**真正的 Minecraft Java 版客户端**（其网络层就是 Netty 全栈），范围覆盖到 1.21 与 Forge/Fabric。
- 最新版本已实测跑通 Minecraft 26.1 / 26.2 / 26.3（26.3 要求 Java 25）——与 PickaxeCraft 锁定的协议版本区间一致。
- PojavLauncher 本体已宣布停止维护，但活跃后继（Fold Craft Launcher 基于 Pojav 后端 + HMCL 核心、ZalithLauncher2 等）保持更新，生态未中断。
- 补充佐证：Termux 路径同样成熟，社区已有完整工具链在 Android 上跑 Minecraft Java 版服务端。

**关键推论：PojavLauncher 证明的是「自带 OpenJDK」这条运行时路径可行；它不直接证明「ART + D8 反糖」路径可行。** 两条路径的 JVM 环境不同，一个成功不能推断另一个成立。

### 3.3 Android 上的两条运行时路径

| 维度 | 路径 A：ART + D8 反糖（当前架构预设） | 路径 B：自带 OpenJDK（PojavLauncher 先例） |
| --- | --- | --- |
| 运行时 | Android 应用进程内的 ART | 打包的 OpenJDK JRE |
| 字节码处理 | Java 21 → D8 反糖 → ART 执行 | 原生 class 文件 → 标准 JVM 执行 |
| Netty 表现 | 未验证；4.2.x 系列在该路径上有 VerifyError 实测报告 | 已被 Minecraft 原版验证（26.3 可跑） |
| Java 21 字节码策略 | 必须保留（D8 反糖依赖） | 可放宽，但保留无害 |
| 宿主形态 | 原生 Android App，可被其他 App 嵌入 | PojavLauncher/FCL 生态，或自行打包 JVM |
| 当前架构覆盖 | 是（protocol-core Java 21 字节码 + `verifyBytecode` 的假设前提） | 否，但技术上可行 |

### 3.4 参照项目：Mindustry / Arc 框架

Mindustry 的参考价值不在「它也在 Android 上跑」（它的网络层其实不用 Netty，用的是自家 Arc 框架的 `ArcNetProvider`，一个基于原生 socket 的轻量实现），而在于其**架构分层方式**：

- **`Net` 门面 + `NetProvider` SPI + 默认后端**：上层代码完全不感知传输实现；
- **跨平台靠「核心模块 + 平台后端模块」**：desktop 与 Android 共用同一份 core 字节码；
- **网络协议自设计**（`Packets` 类），没有 MCPL 那种「协议实现与 Netty 管道耦合」的包袱——但这得益于 Mindustry 同时是客户端和服务端作者、没有外部协议对齐压力。

**对 PickaxeCraft 的映射启示：**

1. **传输 SPI 不是「要不要」而是「何时」的问题**。PickaxeCraft 当前卡在 MCPL 的 `Session.getChannel()` 直接返回 Netty `Channel`，没有 SPI——这正是「文档说没有可替换传输」的根源。若决定支持 ART 路径，参照 Arc 的 `NetProvider` 模式引入 SPI 是正确形态。
2. **字节码纪律与 Mindustry 一致**：强制 `protocol-core` 出 Java 21 字节码（major 65）同时服务两条 Android 路径，价值比原评估更高，必须维持。
3. **不要照抄 Mindustry 的传输自研**：PickaxeCraft 对齐 Java 版 776，协议细节必须复用 MCPL，这一点不该动摇。

### 3.5 排除的其他选项

- **Android NIO + 从零自写协议**：不推荐。这是决策 0001 已否决的自研路线，Android 化不会让它更有吸引力——776 的 256 个数据包、注册表 NBT、压缩/加密状态机的工作量不变，且失去 MCPL 的生产验证。除非生态出现原生 KMP、不依赖 Netty、达到 Geyser 级成熟度的 Java 版协议库，否则这条路继续关闭。
- **PojavLauncher 类方案**：是在 Android 上跑完整 Minecraft Java 版游戏（含渲染）的启动器，与 PickaxeCraft 的 Headless 库定位正交。它的存在说明 Android 上跑完整 JVM 在生态里成立，间接支持自带 OpenJDK 路径（路径 B）的可行性。

## 4. 版本漂移：季度 Drop 让「锁定 26.2」的成本比直觉高

Minecraft 在 2026 年切换为「年度版本号 + 一年多次 Drop」节奏：

| 版本 | 发布窗口 | 最低 Java |
| --- | --- | --- |
| 26.1 | 2026-03 | Java 25 |
| 26.2（当前锁定） | 2026-06 | Java 25 |
| 26.3 | 2026-09 | Java 25 |
| 26.4 | 2026-10 起快照 | Java 25 |

这意味着：

- 协议号**约每季度推进一次**，每次都要求 MCProtocolLib 与 Minestom 双侧同步升级；MCPL 上游 `maven-metadata` 已显示 26.3-2 为 latest，锁 26.2 实际上已在落后一个功能版本；
- 「升级必须两侧同时改并重跑真实握手」是正确约束，但手工执行每季度一次会成为持续摩擦。

## 5. 并发模型补充：跨线程边界显式化

MCProtocolLib 的收包回调发生在 **Netty EventLoop 线程**上，会话 Actor 跑在协程调度器上，两者之间的桥接是现有文档的缺失项，应在 architecture.md §5 写明：

- 回调里是否做任何业务判断（应为否）；
- 事件转换在哪个线程完成（建议：EventLoop 线程只做解包与类型转换，转换后立即入队，业务判断全部在 Actor 侧）；
- 背压触发时回调侧行为：丢弃哪个方向的包、如何向调用方上报、绝不静默。

跨线程边界正是这类库后期 bug 的高发区，应在 M1 的 Session API 设计中一并落定。

## 6. 实现路径评估：一处时序矛盾与一个正确归因

1. **M3 时序矛盾**（本评估最重要的可执行建议）：roadmap §1 写着「先验证风险最高的链路……当前最大风险是 Android 上的 Netty」，但 M3 排在 M2 之后。M0 的探针工程已能在 120 行内完成 status + login，缩减版 Android spike 的成本是几天而非一个里程碑。**建议把缩减版 Android spike 提前到 M1 并行**；若 Netty 挂了，M2 的部分设计（如区块缓存内存策略）可据此调整。
2. **harness 的出生实例缺口已修复，但出生仍未验收**。当前实现已注册 `AsyncPlayerConfigurationEvent` 并设置 `spawningInstance`，联调日志出现 `player.configuring`；这推翻了本文早前“尚未配置出生实例”的现场描述。现有测试只断言进入 GAME，尚未断言 `player.spawned`，因此出生与后续世界同步继续作为 M2 门控，不能标记完成。

## 7. 决策清单

### 决策 1：缩减版 Android spike 提前到 M1 并行执行

- 范围限定：只测 status 查询，不做完整登录链路，不写支持矩阵，不引入 AGP/KMP。
- 目的：在 M2 投入完整工作量之前获得路径 A（ART）的初步证据。
- 原 M3 保留，升级为「双路径完整验证」（见决策 3）。

### 决策 2：M1 期间对 MCProtocolLib 做 API 稳定性评估

- 评估内容：除 `Session.getChannel()` 之外是否存在需要底层干预的场景（自定义压缩管道、日志钩子、底层错误恢复等）；这些场景走上游 PR 还是接受 fork。
- 不要求 M1 期间得出结论，但要求形成书面评估记录。
- 补充动作：把「EventLoopGroup 归调用方注入还是 Session 内部持有」写成显式 API 决策，参考社区已有先例（调用方提供 EventLoopGroup），在 M1 的 Session 生命周期 API 中落实。

### 决策 3：M3 spike 升级为双路径验证

- **路径 A（ART）**：D8 反糖后的 AAR 在模拟器/真机跑 status + login，重点采集：Netty 4.2.1 的 `UnpooledDirectByteBuf` 加载结果、内存池行为、设备休眠时的连接存活、`minSdk` 下限。
- **路径 B（自带 OpenJDK）**：在 PojavLauncher/FCL 环境跑 `:app` 的 CLI，或验证「打包 OpenJDK + protocol-core」的可行性。预期直接通过（有 Minecraft 原版 26.3 先例）。
- 两条路径的结论分别写入架构文档；支持矩阵只在有结论后更新。

### 决策 4：Android 宿主形态作为待决产品问题记录在案

- 若接受「Android 宿主为 PojavLauncher/FCL 类自带 JVM 启动器」：路径 B 直接成立，`protocol-core` 现有设计无需改动，Android 主要风险归零。
- 若要求原生 ART 嵌入：需要 fork MCProtocolLib、抽出编解码层、自写传输层，并在 `protocol-core` 引入传输 SPI（参照 Arc `NetProvider` 模式 + gRPC `grpc-okhttp` 分层方式）。
- 两条路径技术工作量差一个数量级，最终选择属产品决策；技术侧的义务是把两条路径的成本与证据写清楚。

### 决策 5：版本升级流程脚本化 + 上游感知

- 把「升级演练」做成脚本化流程：改协议库与 Minestom 两个版本号 → 重跑 `ClientInteropTest` → 记录差异。
- CI 增加每周任务：用 MCProtocolLib 最新版（26.3-2 及后续）跑探针工程，提前感知上游 breaking change。
- 不改变「锁定 26.2 跟随 Minestom」的当前决策。

### 决策 6：Android spike 失败时的 Plan B（预案，非当前承诺）

- **方案**：fork MCProtocolLib → 抽出 Packet/Codec 层（编解码逻辑与 Netty 管道耦合度有限，MIT 许可允许）→ 用 OkHttp socket 层或 **Ktor network**（基于 java.nio，Android 原生可用，挂起 API 与本项目协程模型契合）重写传输层 → 自建发布链路（fork 后不再依赖 opencollab 仓库）。
- **注入点**：MCPL 的 `ClientNetworkSession` 已接受 `ChannelFactory`，fork 时把工厂扩展到非 Netty 实现即可，不需推翻库结构。
- **代价**：与上游 26.x 升级解耦，每季度 Drop 需自行合并——决策 0001「版本漂移」代价的放大版，因此仅作为 spike 双双失败后的路径，不预防性启动。
- **兜底交付**：若 Android 库形态最终不可行，提供 Termux + proot 跑完整 JVM 的交付路径（`:app` jar 原样运行，零代码改动），作为「Android 设备上可用」的最低保障，不替代嵌入形态。

### 决策 7：维持不变的部分

- **MCProtocolLib 作为协议后端**：决策 0001 结论经复查维持。JVM 生态内的替代品（kmcprotocol、kt-mc-packet 等）均无 Geyser 级生产验证；hl-mc-kt 等同类项目最终也站在 MCPL 之上；「MCPL + 自研上层」是这条赛道的事实路线。Android 化不改变该结论——Android 上从零自研协议只会更不可行。
- **Java 21 字节码纪律**：同时服务两条 Android 路径（ART 反糖、OpenJDK 直接加载），价值比原评估更高，必须维持。
- **单 Actor 会话模型、有界队列、单一写入口等并发设计**：维持，是流式协议处理的正确形态。

### 决策 8：Minestom 集成边界与单人游戏归属

- **核心库不直接集成 Minestom**：`protocol-core`、`client-core` 和其他共享发布产物不得依赖或暴露 Minestom 类型。现有 `testing:minestom` 仅是测试宿主，不是运行时架构的一部分。
- **单人游戏是外部 Desktop 宿主的可选能力**：最终图形客户端可在独立仓库建立 Java 25 组合模块，负责启动、配置和关闭内嵌 Minestom；核心客户端仍通过正常协议连接本地服务端，不直接读写服务端世界对象。
- **Java 版本相互隔离**：Minestom 自身使用 Java 25，因此内嵌服务端的宿主必须使用 Java 25；共享客户端产物继续保持 Java 21 字节码，不能为了单人模式上调，否则会破坏 Android/RoboVM 的复用目标。
- **平台能力分别声明**：Desktop 可以承诺经实测的单人模式；Android/iOS 默认只承诺连接外部服务端，除非对应平台另行通过 Minestom Java 25 的运行时验证。
- **生命周期归宿主**：先启动本地服务端再连接，退出时先关闭客户端 Session 再停止服务端；端口冲突、服务端启动失败与异常退出必须转化为外部客户端可处理的错误，不进入核心连接 API 的隐含副作用。

### 决策 9：下游渲染自研；桌面双后端对齐原版；libGDX 仅作移动端平台壳

- **归属**：渲染路线只约束外部图形客户端，本仓库不增加 GL、GLES、Vulkan 或着色器依赖，公共核心继续只暴露会话与只读世界模型。
- **渲染器完全自研**：meshing、shader、相机、剔除与实体渲染不使用 libGDX 的 graphics API（`Mesh`/`ShaderProgram`/`Camera`/scene2d 不进入渲染路径）。渲染代码面向自维护的最小 GL 调用面，以 GLES 2.0/3.0 语义为共同子集；桌面 GL 后端承担 ES 与 desktop 方言的轻量差异（`#version`、`attribute/varying` 转换等）。
- **桌面双后端，对齐原版**：Windows/Linux/macOS 宿主不依赖 libGDX，图形入口为 LWJGL3（GLFW + GL/Vulkan 绑定）。OpenGL 为默认可用路径与回退，实验性 Vulkan（LWJGL Vulkan 绑定）为演进目标——与 MC Java 26.2 的双后端策略同构：不因 Vulkan 实验性阻塞 OpenGL 交付，也不因 OpenGL 可用而冻结 Vulkan 演进；Vulkan 1.2、dynamic rendering、push descriptors 等要求以原版实验后端为参照。
- **libGDX 只作移动端平台壳**：Android/iOS 宿主使用 libGDX 仅限生命周期（Activity/Fragment）、GL 上下文创建与丢失重建、输入事件、文件 IO 与 RoboVM 宿主；渲染代码不 import libGDX graphics 类型，GL 调用直接走平台 GLES 绑定。桌面 ANGLE 路线（官方 `gdx-lwjgl3-angle` 与第三方 `gdx-lwjgl3-angle-vulkan`）随之废止——后者本质是 libGDX 桌面后端；相关调研结论保留用于移动端（Android 10+ 系统 ANGLE、iOS MetalANGLE）。
- **平台后端**：Windows/Linux = OpenGL 默认 + 实验性 Vulkan；macOS = OpenGL（上限 4.1，已弃用但可用，长期观察 MoltenVK/Metal 路线）；Android = libGDX 壳 + 原生 GLES 2.0/3.0；iOS = libGDX/RoboVM 壳 + MetalANGLE（评估不变）。必须记录 renderer/vendor、后端和版本，由运行时证据而非依赖名称声明能力。
- **验收门控**：外部客户端必须用同一测试场景验证 OpenGL 默认路径、Vulkan 实验路径与二者切换，并覆盖 natives 加载、窗口/上下文重建、shader 在 ES/desktop 两种方言下的编译，以及移动端上下文丢失后的资源重建。未通过前只能声明“OpenGL 路径可用”，不能声明“已支持 Vulkan”。
- **成本边界**：桌面脱离 libGDX 意味着音频（LWJGL OpenAL 直接接入）、UI 与位图字体改为外部客户端自研或另行选型；这些本属游戏域工作，不回流本仓库。

## 9. 回到本决策的条件

任一成立时应重新评估本文档结论：

- MCProtocolLib 上游出现结构上无法 fork 适配的破坏性变更；
- 生态中出现原生 KMP、不依赖 Netty、达到 Geyser 级成熟度的 Java 版协议库；
- Minecraft Drop 节奏再次变化导致季度升级成本不可承受；
- PojavLauncher 生态（含 FCL/Zalith 等后继）出现长期停滞，路径 B 失去宿主载体；
- 自研桌面双后端的成本被实测证伪（如 shader 双方言转换失控、Vulkan 后端长期无法对齐原版实验行为）；
- RoboVM spike 失败使 iOS 无宿主，libGDX 的剩余价值需要重估。

## 10. 参考

- Netty 官方不支持 Android；4.2.4+ 在 Android 8–12 的 `UnpooledDirectByteBuf` VerifyError 实测报告
- Netty 4.2.16.Final 安全公告（11 项 CVE）与 4.2 迁移指南（端点校验默认行为变更）

- PojavLauncher 及后继（Fold Craft Launcher、ZalithLauncher2）：Android 上运行 Minecraft Java 版 26.1–26.3 的实测先例；PojavLauncher 本体已停止维护，生态由后继延续
- Minecraft Java 版本与 Java 版本对应表：26.1–26.3 均要求 Java 25
- Minecraft 26.4 快照（Snapshot 2 / Snapshot 5）发布记录：季度 Drop 节奏的证据
- MCProtocolLib 上游 `maven-metadata.xml`：latest 为 26.3-2，仓库 `repo.opencollab.dev`
- rfresh2/MCProtocolLib fork：深度改造可行性的先例，及上游 API 无稳定性承诺的证据
- Mindustry / Arc 框架：`Net` + `NetProvider` 传输 SPI 分层范式（参照分层结构，不照抄自研传输）
- Minecraft Console Client 的 Termux + proot 运行文档（Android 上跑 JVM 的兜底路径先例）
